/avril · /axel commands PLAN

Implement /avril and /axel

Goal: type natural language after a slash command and get the correct planning or execution conductor — e.g. /avril please give me a summary of the current project state or /axel run the next blessed PBI.

Mechanism: OpenCode custom commands (markdown templates + $ARGUMENTS) + dedicated agents + existing avril/axel skills under .agents/skills/.

1. Recommended shape (v1)

User types /avril $ARGUMENTS
        │
        ▼
.opencode/command/avril.md   ← prompt template + preflight shell
        │  agent: avril
        ▼
.opencode/agent/avril.md     ← conductor persona (orchestrator)
        │  skill tool loads
        ▼
.agents/skills/avril/SKILL.md + personas under .agents/agents/
        │
        ▼
Pinto board / Blessed Backlog / planning-only stop

Same pattern for /axel → agent axel → skill axel. Keep one entrypoint per loop; route intent from free-text $ARGUMENTS, not a dozen micro-commands.

2. Why not only skills?

  • Skills load on demand via the skill tool; they are not slash-addressable by themselves.
  • Commands are first-class in the TUI (/ menu) and inject a fixed prompt + optional shell preflight.
  • Agents pin permissions/mode so AVRIL cannot “helpfully” implement, and AXEL stays conductor-only unless generation is delegated.

3. UX contract

InvocationBehavior
/avril Default: status — board, blessed set, ready PBIs, open questions. No mutations.
/avril <free text> Interpret as planning request (status, propose, review item, bless loop, summarize). Never implement code.
/axel Default: next ready blessed PBI summary + ask confirm before execute.
/axel <free text> Execute / status / evidence / board move per AXEL intake gate. Conductor only.

Optional verb prefixes (documented, not required): status, plan, review T-1, next, run T-1, help. Free English always works via the same router in the command template.

Portability: later copy the same four files into templates/harness/ + harness-bootstrap so new projects get /avril and /axel.

5. Command template design

5.1 Preflight (shell injection)

Each command starts with a short status dump so “summary of project state” is cheap and consistent:

Git:!`git status -sb && git log --oneline -8`
Progress tail:!`tail -n 40 progress.md 2>/dev/null || true`
Features snapshot:!`python3 -c "…" # pending commits from features.json`
Pinto (if present):!`command -v pinto >/dev/null && pinto list --json || echo "no pinto"`
Blessed summary path:!`ls docs/plans/*blessed* 2>/dev/null || true`

Keep preflight read-only. Fail soft if tools missing.

5.2 Prompt body (sketch)

---
description: AVRIL planning conductor (status, propose PBIs, blessing loop)
agent: avril
---

You are the AVRIL conductor. Load skill `avril` and `code-writer` via the skill tool first.
Recite the One-Sentence Mandate, then handle the user request.

User request:
$ARGUMENTS

If $ARGUMENTS is empty, run **status**: board + blessed set + ready items + blockers.
Routing hints (non-exclusive):
- status / summary / state → read-only project + backlog report
- plan / propose / backlog → Generator proposes PBIs (Pinto preferred)
- review / bless → PO→QA→CTO cycle on named ids
- help → list capabilities; do not implement code

Hard rules: planning-only stop; never write production code; explicit BLESS tokens;
prefer Pinto; emit Blessed Backlog Summary when loop completes.

Mirror for axel.md: load axel + language stack; intake gate; PETC; never write code as conductor; default empty args = next ready PBI + confirm.

6. Agent design

avril

  • mode: primary (Tab-switchable) or subagent if you only want slash invoke
  • permission.edit: allow for board/docs only if needed; prefer ask on broad edits
  • bash: allow read-only git/pinto/jq; ask on writes
  • Prompt: thin — point at skill SoT, don’t duplicate full SKILL.md
  • color: e.g. planning blue

axel

  • Same mode choice as avril
  • edit: ask (conductor delegates generation; should rarely edit itself)
  • task: allow code GAN / rust-team-lead style subagents
  • Intake gate enforced in agent prompt + skill
  • color: e.g. execution amber

Recommendation: mode: primary so Tab can switch Plan-like conductors; commands still force the right agent via frontmatter agent:.

7. Permissions & safety

  • AVRIL must not implement. Command + agent text restate planning stop; optional permission.edit: ask globally for avril agent.
  • AXEL intake gate. Refuse unblessed ids unless user explicitly authorizes in $ARGUMENTS.
  • Pinto writes only when user request clearly mutates backlog (propose/revise), not on status.
  • No secrets in command templates; no force-push bash allows.

8. Stacked delivery

cmd-01 Scaffold — .opencode/command/{avril,axel}.md + agent/{avril,axel}.md minimal; empty-args = status; load skills. Restart opencode smoke test.
cmd-02 Preflight — shell injections for git/progress/features/pinto; document required tools.
cmd-03 Router polish — help text, verb hints, examples in command descriptions; AGENTS.md one-liner for /avril /axel.
cmd-04 Bootstrap portability — copy into templates/harness/ + harness-bootstrap; short book/README mention.

9. Acceptance criteria

  • □ Typing /avril appears in command palette with clear description
  • □ /avril please give me a summary of the current project state yields read-only status using preflight + board (no code edits)
  • □ /avril with empty args ≡ status behavior
  • □ /axel empty args reports next blessed/ready PBI or explains intake failure
  • □ Agents load avril/axel skills (visible in skill tool list from .agents/skills/)
  • □ AVRIL session does not implement production code when asked to “just build it”
  • □ After config change, docs note: restart opencode
  • □ just harness-validate still passes (no docs-verify breakage)

10. Non-goals (v1)

  • Separate slash commands per verb (/avril-status, /avril-plan, …) — free text is enough
  • Rewriting AVRIL/AXEL skills (commands wrap them)
  • GUI beyond OpenCode TUI command menu
  • Auto-running full blessing loops without user intent in $ARGUMENTS
